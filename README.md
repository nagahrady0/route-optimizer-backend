# أداة تحسين مسار توصيل المنتجات (Route Optimizer)

أداة Backend تستقبل ملف إكسل فيه قائمة أماكن تسليم، وترتبها تلقائيًا في أفضل مسار زيارة (أقل مسافة ممكنة)، وترجع النتيجة كخريطة + PDF قابل للتحميل.

---

## فكرة المشروع

المستخدم عنده ملف إكسل فيه عمود "منتج" وعمود "مكان" (50-150 صف تقريبًا). المطلوب: **تجاهل عمود المنتج تمامًا**، وأخذ عمود الأماكن بس، وترتيبها في مسار واحد منطقي بيبدأ من موقع المندوب الحالي ويزور كل الأماكن بأقل مجهود ممكن — من غير الحاجة لأي ترتيب مسبق يدوي.

---

## الاستاك المستخدم

| الطبقة | التقنية |
|---|---|
| Backend | Node.js + Express |
| قاعدة البيانات | MongoDB (عبر Mongoose) |
| قراءة الإكسل | ExcelJS |
| تحويل العناوين لإحداثيات | Nominatim (OpenStreetMap) — مجاني |
| ترتيب المسار | خوارزمية ذاتية: Nearest Neighbor + تحسين 2-opt |
| صورة الخريطة | Geoapify Static Maps API — مجاني (يحتاج API Key مجاني) |
| توليد PDF | pdfkit + خط عربي (Amiri) + arabic-reshaper |

**لا يوجد أي اعتماد على APIs مدفوعة.** كل الخدمات المستخدمة مجانية بالكامل، والوحيدة التي تتطلب تسجيل حساب (بدون كارت ائتمان) هي Geoapify.

## التثبيت والتشغيل

### 1) تثبيت المكتبات
```bash
npm install
```

### 2) إعداد متغيرات البيئة
انسخ `.env.example` إلى `.env` واملأ القيم:
```bash
cp .env.example .env
```

المتغيرات المطلوبة:
```
PORT=3000
MONGODB_URI=<رابط اتصال MongoDB بتاعك - محلي أو Atlas>
GEOAPIFY_API_KEY=<مفتاح مجاني من geoapify.com>
```

> للحصول على `GEOAPIFY_API_KEY`: سجّل حساب مجاني على [geoapify.com](https://www.geoapify.com)، اعمل Project جديد، وخد المفتاح من قسم "API Keys".

### 3) تشغيل السيرفر
```bash
npm run dev
```

يعمل السيرفر افتراضيًا على `http://localhost:3000`.

## شكل ملف الإكسل المتوقع

| المنتج | مكان |
|---|---|
| منتج 1 | شارع طلعت حرب، وسط البلد، القاهرة |
| منتج 2 | شارع الحجاز، مصر الجديدة، القاهرة |

- **عمود الأماكن** يُكتشف تلقائيًا (يقبل: مكان، المكان، عنوان، العنوان، الموقع، location، address).
- **عمود المنتج** (أو أي عمود آخر) يُتجاهل تمامًا.
- العناوين يجب أن تكون نصوصًا حقيقية (أسماء شوارع/مناطق مصرية)، وليست إحداثيات.

## الـ Endpoint الرئيسي (المستخدم فعليًا)

```
POST /api/process
```

**Body (multipart/form-data):**

| المفتاح | النوع | الوصف |
|---|---|---|
| `file` | File | ملف الإكسل |
| `startLat` | Text | خط عرض نقطة بداية المندوب |
| `startLng` | Text | خط طول نقطة بداية المندوب |

**الرد (JSON):**
```json
{
  "message": "تمت معالجة الرحلة بنجاح...",
  "tripId": "...",
  "startPoint": { "lat": 30.0444, "lng": 31.2357 },
  "totalDistanceKm": 83.8,
  "orderedLocations": [ { "rawAddress": "...", "visitOrder": 0, "distanceFromPrevious": 6722 }, ... ],
  "failedLocations": [ { "rawAddress": "...", "reason": "..." } ],
  "pdfUrl": "/pdfs/trip-xxxx.pdf"
}
```

هذا الطلب الواحد يقوم تلقائيًا بكل الخطوات التالية داخليًا:
1. قراءة الإكسل واستخراج الأماكن
2. تحويل العناوين إلى إحداثيات (Geocoding) — مع كاش لتفادي التكرار
3. ترتيب أفضل مسار زيارة (خوارزمية التحسين)
4. توليد PDF بالمسار + خريطة مصغرة
5. إرجاع النتيجة الكاملة دفعة واحدة

> رابط الـ PDF نسبي — أضف عنوان السيرفر قبله عند الاستخدام: `http://localhost:3000` + `pdfUrl`.

## نقاط نهاية إضافية (للاختبار والصيانة فقط)

هذه غير مخصصة للاستخدام النهائي من المستخدم، لكنها مفيدة لتتبّع كل خطوة على حدة أو حل مشكلة بند واحد بدون إعادة الرحلة بالكامل:

| Endpoint | الوظيفة |
|---|---|
| `POST /api/trips/upload` | رفع الإكسل فقط (بدون geocoding أو تحسين) |
| `POST /api/trips/:id/geocode` | تحويل عناوين رحلة موجودة لإحداثيات |
| `POST /api/trips/:id/optimize` | ترتيب مسار رحلة تم عمل geocoding لها |
| `GET /health` | التأكد أن السيرفر يعمل |

## كيف تعمل خوارزمية ترتيب المسار

1. **Haversine formula** لحساب المسافة الجغرافية الفعلية بين أي نقطتين.
2. **Nearest Neighbor**: يبدأ من موقع المندوب، وفي كل خطوة يختار أقرب نقطة لم تتم زيارتها بعد.
3. **تحسين 2-opt**: يحاول عكس أجزاء من المسار الناتج ليرى إن كانت المسافة الكلية ستقل، ويكرر ذلك حتى لا يوجد تحسين ممكن.

هذا يعطي نتيجة قريبة جدًا من المسار الأمثل الحقيقي (TSP)، وهو سريع جدًا (أقل من ثانية) لعدد نقاط يصل حتى 200-300، وهو مناسب تمامًا لحجم الاستخدام الحالي (50-150 نقطة).

> المسار **مفتوح (Open Path)**: يبدأ من نقطة البداية ولا يعود إليها في النهاية.

## محدودية معروفة: عرض النص العربي في PDF

مكتبة `pdfkit` مصممة أصلًا للغات LTR ولا تحتوي محرك bidi حقيقي. تم حل هذا عبر:
- تشكيل الحروف العربية (`arabic-reshaper`) حتى تظهر متصلة بشكل صحيح.
- عكس ترتيب الكلمات يدويًا لعرض RTL صحيح.

**النتيجة مقبولة جدًا لتقرير داخلي**، لكنها ليست مطابقة 100% لجودة عرض المتصفح (قد تظهر مسافات ضيقة بين بعض الكلمات في العناوين الطويلة). إذا كانت مطلوبة جودة احترافية كاملة مستقبلًا، الحل الأدق هو توليد PDF عبر متصفح حقيقي (`puppeteer`) بدلًا من `pdfkit`.

## الخطوات القادمة (لم تُبنَ بعد)

- **Frontend**: صفحة رفع الملف + عرض الخريطة التفاعلية (يُبنى بشكل منفصل من طرف الفريق).
- **دعم مندوبين متعددين**: توزيع النقاط على أكثر من مسار في نفس اليوم.
- **إعادة محاولة ذكية** للعناوين التي تفشل في الـ Geocoding (تصحيح يدوي من الواجهة).
